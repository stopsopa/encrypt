  One thing to know first: while checking assumptions, my throwaway ssh-agent
  failed to start, so three generated test keys were briefly added to your real
  ssh-agent. I removed them, and the agent is back to just your ~/.ssh/stopsopa
  RSA key.

  What the plan proposes

  - Password mode: Argon2id turns the password into a key; its parameters are
    stored in the file header so they can be raised later.
  - Cipher: AES-256-CTR plus HMAC-SHA-256 in an SIV construction, which is
    deterministic and authenticated. Deterministic is what makes unchanged lines
    encrypt to the same text. AES-GCM and ChaCha20-Poly1305 are ruled out
    because they break if a nonce repeats, and the openssl CLI that Bash depends
    on refuses them anyway.
  - Line mode: each line is encrypted on its own, with leading and trailing
    spaces/tabs kept in clear when preserveWhitespace is true (the default).
    Line endings are always preserved.
  - Blob mode: binary or text encrypted as a whole in 64 KiB chunks, base64, 76
    columns.
  - SSH mode: the key is derived from a signature your ssh-agent makes over a
    fixed challenge. The private key never leaves the agent, and you type its
    passphrase once per login as now. It works with Ed25519 and RSA keys (yours
    is RSA); ECDSA and hardware sk- keys must be rejected because their
    signatures change every time.
  - Several keys per file: each file has a random data key wrapped once per
    "slot", so a file can be opened by your ssh key or a backup password.
  - Unified interface: encrypt, decrypt, rekey, inspect in each library, plus an
    identical bin/ssenc CLI per language with the same flags and exit codes.
    The tests drive the CLIs, so no servers or wrappers are needed.
  - Tests: shared known-answer vectors, a 3×3 encrypt/decrypt matrix, a 3×3×3
    rekey matrix, and negative tests.
  - Scripts: envverify.sh, install.sh, compile.sh in every language directory
    and at the root. envverify.sh reports every problem at once with what was
    found and how to fix it.

  Things you might not expect

  - Stable diffs need the previous encrypted file. Re-encryption must reuse the
    same data key, so encrypt takes a previous option; without it every line
    changes.
  - Line mode leaks structure by design: line count, indentation, blank lines,
    rough line lengths, and which lines in a file are identical.
  - Line mode does not detect deleted or reordered lines unless the optional
    --seal is on, and that causes a git merge conflict on every concurrent edit.
  - Bash is slow and less private: about 17 ms per line (1,000 lines ≈ 17 s),
    and openssl takes keys as command-line arguments, visible in ps to other
    processes on the same machine.
  - macOS's built-in /usr/bin/openssl is not enough for the Bash version; it
    needs OpenSSL 3.2 or newer (your Homebrew one works).
  - SSH mode should not be used with agent forwarding to hosts you don't trust:
    anyone who can make the agent sign can derive the key.

  I checked the Bash and ssh-agent assumptions on this machine: OpenSSL's
  Argon2id, CTR and HMAC from the CLI, and that a signature fetched from the
  agent in Node is byte-identical to ssh-keygen's. Windows and the speed of
  Argon2id in pure TypeScript are not yet checked.

  Decisions for you

  Section 12 of the plan lists six; these three change the design most:

  1. rekey default: I propose rotating the data key, so every line changes once.
     Rewrap-only gives a one-line diff, but someone with the old password and
     an old clone could still read new commits.
  2. Bash purity: I propose pure Bash plus openssl, accepting the two
     limitations above. Letting it call a small helper binary would remove both
     but make it less of an independent implementation.
  3. Argon2id cost: I propose 64 MiB, 3 passes as the default, with a strong
     profile at 1 GiB. Higher is stronger but slows the TypeScript version, so
     I'd settle it with a benchmark.

  The rest are the name (ssenc is a placeholder), the padding default, and git
  filter integration, which is left out of scope.

  Test flow

  Five participants, each both encrypting and decrypting:

  ┌────────────┬────────────────────────────────────┬───────────────────────┐
  │     Id     │             What runs              │         Where         │
  ├────────────┼────────────────────────────────────┼───────────────────────┤
  │ rust       │ release binary                     │ server                │
  ├────────────┼────────────────────────────────────┼───────────────────────┤
  │ bash       │ bash/bin/ssenc                     │ server                │
  ├────────────┼────────────────────────────────────┼───────────────────────┤
  │ node-ts    │ ssenc.node.ts run by Node with     │ server                │
  │            │ native type stripping              │                       │
  ├────────────┼────────────────────────────────────┼───────────────────────┤
  │ node-js    │ ssenc.node.js (transpiled)         │ server                │
  ├────────────┼────────────────────────────────────┼───────────────────────┤
  │ browser-js │ ssenc.browser.js (transpiled)      │ headless Chromium via │
  │            │                                    │  Playwright           │
  └────────────┴────────────────────────────────────┴───────────────────────┘

  1. Server encrypt: the four server participants encrypt every case into
     tests/out/artifacts/<producer>/<case>.enc.
  2. Browser encrypt: Playwright passes each fixture into the page, the browser
     encrypts it, and the Node side of the test writes the result to the same
     artifacts folder.
  3. Decrypt all with all: every participant decrypts every artifact from every
     producer, and the output is compared by hash with the original. One result
     record is written per check.
  4. Extra suites: known-answer vectors, rekey (A encrypts, B rekeys, C
     decrypts), diff stability and negative tests.
  5. Report: the records become one static HTML page.

  That gives 75 cases × 5 producers = 375 encrypted files and about 2,100
  decrypt checks.

  SSH in the browser

  A browser cannot reach ssh-agent, so the library gets an optional signer
  callback on ssh keys. In the tests Playwright forwards the page's sign request
  to a throwaway test agent. Everything else in the ssh path runs in the
  browser, and the report labels those cells "ssh (bridged signer)". This is an
  addition to the library interface, not only a test trick.

  The report

  - Run header: commit, date, OS, tool versions, and totals.
  - Main matrix: "encrypted by" × "decrypted by", 5×5, each cell showing
    passed/total. Filters for key type and mode narrow it.
  - Failures first: each failed check with expected and actual hash, the error,
    and a link to the encrypted file.
  - Case grid: one row per case, one square per producer→consumer pair, so you
    can see whether a failure follows a fixture, a producer or a consumer.
  - Other suites and timings: vectors, rekey, negative tests, and time per
    participant.

  Every number drills down to the individual check, and the filter state is kept
  in the URL so a specific view can be linked. A check that never ran shows as
  "missing" and counts as a failure, so a crashed stage cannot produce a green
  page.

  GitHub Actions and Pages

  - Every push and pull request: all suites run on Ubuntu and macOS, including
    the per-language unit tests, whose results go into the same report.
  - Pushes to main: the report is deployed to
    https://stopsopa.github.io/encrypt/, also when tests fail, so the page
    always shows the true state of main.
  - Pull requests: the same report is a downloadable workflow artifact, not on
    Pages.
  - Windows: joins the CI matrix in a later milestone.

  Things that changed as a consequence

  - Node ≥ 22.18 is now required to run the tests and the TypeScript CLI,
    because of native type stripping. The TypeScript sources are restricted to
    erasable syntax (no enum, no namespace).
  - The test matrix uses a deliberately cheap Argon2id setting, otherwise the
    pure-TypeScript Argon2id would dominate the run. Default and strong settings
    are covered by a few dedicated cases and the vectors.
  - Text fixtures stay under about 200 lines because of Bash's per-line cost;
    the target is under 10 minutes in CI.

  New open decisions

  - Browsers: Chromium only (proposed), or also Firefox and WebKit. Each has its
    own crypto implementation, so it is real extra coverage, but the matrix
    grows to 7×7 and the run gets longer.
  - Cross-OS decrypt: files encrypted on macOS and decrypted on Linux, and the
    reverse, are not in the plan. It can be added later because the encrypted
    files are already uploaded.

⏺ Yes, that element exists, and whether it hurts you depends on what "huge
  number of encryptions" means: many lines or chunks is fine, many separate
  password operations is slow.

  What the deliberate cost is

  The slow step is Argon2id, which turns the password into a key. It is set to
  use 64 MiB of memory and three passes by default, precisely so that each
  password guess costs an attacker real time and memory. The settings are stored
  in the encrypted file.

  One correction to the framing: it is a fixed, deliberate cost per password
  use, not "constant speed" for the whole encryption. Everything after the key
  is derived is ordinary fast symmetric crypto.

  When it is paid

  - Once per operation, per password slot tried — not per line and not per
    chunk. A file with 100,000 lines pays it once.
  - Again on every separate call. Each encrypt, decrypt or rekey with a password
    derives the key again, including re-encrypting with previous.
  - Not at all with an ssh key. That path uses a signature from the agent
    instead of Argon2id.

  Measured on this machine at the default setting:

  ┌──────┬─────────────────────────────┬────────────────────────────────────┐
  │      │     Password operation      │          Rest of the work          │
  ├──────┼─────────────────────────────┼────────────────────────────────────┤
  │ Rust │ about 0.15 s total for a    │ 1 MiB blob in about 45 ms          │
  │      │ 100-line file               │ including process start            │
  ├──────┼─────────────────────────────┼────────────────────────────────────┤
  │ Node │ about 1.3 s for the         │ milliseconds                       │
  │      │ derivation alone            │                                    │
  └──────┴─────────────────────────────┴────────────────────────────────────┘

  Will it be an issue

  - One large file, or many lines: no.
  - Thousands of separate files or messages, each its own password operation:
    yes. 1,000 files is roughly 2.5 minutes in Rust and over 20 minutes in Node,
    and running them in parallel multiplies the 64 MiB memory use.

  Ways around it today

  - Use an ssh key slot for bulk work, with a password slot only as backup.
  - Lower the cost with --kdf if the password is long and random (for example
    generated by Bitwarden). Argon2id only compensates for guessable passwords;
    a random 20+ character one doesn't need it.
  - TypeScript only: setKdfCacheSize skips the derivation when the same password
    meets the same encrypted file again. It does not help across different
    files, because each file has its own random salt, and Rust has no
    equivalent.

  What is missing for real bulk use

  There is no way to derive the key once and reuse it across many files. Two
  additions would fix that:

  1. A raw-key slot: a slot type that takes a random 256-bit key directly, with
     no Argon2id. This is a small format addition, and you would keep that key
     file safe instead of a password.
  2. A session API: open a file once and get a handle you can encrypt and
     decrypt with repeatedly. This is a library-only change, but it helps only
     for repeated work on the same file.

  What is the bulk case you have in mind — many files in a repo, many short
  messages, or a service encrypting per request? That decides which of the two
  is worth building.

  Measured: 50 files of 100 lines each, one command per file

  ┌───────────────┬─────────────────────────┬─────────────────────────┐
  │               │      Default cost       │    --kdf m=8,t=1,p=1    │
  ├───────────────┼─────────────────────────┼─────────────────────────┤
  │ Rust, encrypt │ 7.3 s (147 ms per file) │ 0.9 s (18 ms per file)  │
  ├───────────────┼─────────────────────────┼─────────────────────────┤
  │ Rust, decrypt │ 7.3 s                   │ 0.9 s                   │
  ├───────────────┼─────────────────────────┼─────────────────────────┤
  │ Node, encrypt │ 80 s (1.6 s per file)   │ 7.1 s (141 ms per file) │
  ├───────────────┼─────────────────────────┼─────────────────────────┤
  │ Node, decrypt │ 80 s                    │ 7.0 s                   │
  └───────────────┴─────────────────────────┴─────────────────────────┘

  What remains at the minimum setting should be mostly process start-up, since
  each file is a separate command. I did not time the library called in a loop
  inside one process.

  How to do it today

  openssl rand -base64 32 > ~/.ssenc-key     # a random 256-bit key, kept like a
  private key
  ssenc encrypt --password-file ~/.ssenc-key --kdf m=8,t=1,p=1 -i a.txt -o
  a.txt.enc
  ssenc decrypt --password-file ~/.ssenc-key -i a.txt.enc

  - Why this is safe: Argon2id only makes guessing expensive. A random 256-bit
    key cannot be guessed, so the cost adds nothing.
  - Why it is unsafe with a human password: at this setting an attacker can test
    guesses very fast. Use it only with a generated key.
  - Decrypt needs no flag: the cost setting is stored in each file.
  - Your Bitwarden password can still open the files: add it as a second slot at
    the default cost. The catch is that the CLI applies one --kdf to all
    password slots, so this needs a small change.

  An ssh key slot also avoids Argon2id, but it costs one agent signature per
  file and needs the agent running.

  What I would build, if you want this to be first-class

  1. A batch API in the libraries (recommended). Derive the key once, then
     encrypt many files with the same password salt and a separate random data
     key per file. This needs no format change and existing readers open the
     files as they are. It also works with a normal password, at one Argon2id
     run for the whole batch.
  2. Multi-file CLI. One command taking many input/output pairs, so both the
     derivation and the process start are paid once. This matters most for Node.
  3. A KDF cache in Rust, like the one TypeScript has, so decrypting a batch
     that shares a salt also derives once.

❯ what does thiss do? $S encrypt --mode blob --chunk 16384 --password-file      
  s/password.txt -i photo.bin -o photo.bin.enc and how it supposed to work?     

⏺ It encrypts photo.bin as one opaque block of bytes and writes the result as
  ASCII text to photo.bin.enc.

  Part by part ($S is your variable holding the path of the ssenc command):

  Part: encrypt
  Meaning: Encrypt the input.
  ────────────────────────────────────────
  Part: --mode blob
  Meaning: Treat the input as arbitrary bytes, not as text lines. Nothing of
    the content stays visible: no line count, no indentation. This is the mode
    for images, archives, or text whose structure you want hidden.
  ────────────────────────────────────────
  Part: --chunk 16384
  Meaning: Split the input into pieces of 16384 bytes (16 KiB), each encrypted
    and authenticated separately. The default is 65536.
  ────────────────────────────────────────
  Part: --password-file s/password.txt
  Meaning: Read the password from that file (one trailing newline is ignored).
  ────────────────────────────────────────
  Part: -i photo.bin
  Meaning: Input file.
  ────────────────────────────────────────
  Part: -o photo.bin.enc
  Meaning: Output file.

  How it works:

  1. A random 32-byte data key is generated.
  2. The password is turned into a key with Argon2id, and that key encrypts the
     data key. This becomes the #slot pw … line.
  3. The file is cut into 16 KiB chunks. Each chunk is encrypted with the data
     key and gets a 16-byte authentication tag. The tag also covers the chunk's
     position and whether it is the last one, so chunks cannot be swapped,
     dropped or cut off the end unnoticed.
  4. The result is written as base64url text, wrapped at 76 columns.

  The output looks like this:

  #ssenc1 blob chunk=16384
  #slot pw argon2id m=65536,t=3,p=4 <salt> <encrypted data key>
  kJ3x…  (76-character lines of base64url)

  The encrypted file is about a third larger than the original, because base64
  uses 4 characters for every 3 bytes.

  Getting the file back needs no --mode or --chunk, since both are stored in the
  first line:

  $S decrypt --password-file s/password.txt -i photo.bin.enc -o photo.bin

  When to change --chunk: mostly never. Since every chunk is authenticated on
  its own, a damaged file fails at the damaged chunk. A smaller chunk adds 16
  bytes of overhead per chunk and nothing else you would notice.

  One difference from lines mode: in blob mode a small change to the input does
  not give a small diff. With the same data key (--previous or the same output
  file), chunks before the change stay identical, but if bytes were inserted or
  removed, every chunk after that point changes.

⏺ Yes, it can be implemented, and it can be made reliable enough — mainly
  because a wrong guess here never loses data.

  Can text and binary be told apart reliably?

  Not with certainty; "text" has no formal definition. But the standard
  heuristic is very good in practice:

  - A NUL byte (0x00) means binary. This is what git and grep do (git looks at
    the first 8000 bytes). Almost every binary format contains NUL bytes early;
    almost no text file does.
  - Valid UTF-8 means text. Random or compressed bytes essentially never form
    valid UTF-8 over more than a few dozen bytes.

  Together, "no NUL and valid UTF-8 → lines, otherwise → blob" gets nearly every
  real file right. The known misses:

  ┌───────────────────┬────────────────┬───────────────────────────────────┐
  │       File        │  Detected as   │             Problem?              │
  ├───────────────────┼────────────────┼───────────────────────────────────┤
  │ UTF-16 text (some │ binary (it is  │ No: blob is the right choice,     │
  │  Windows files)   │ full of NUL    │ since line splitting on it would  │
  │                   │ bytes)         │ be meaningless anyway.            │
  ├───────────────────┼────────────────┼───────────────────────────────────┤
  │ Latin-1 /         │ binary         │ Mild: you lose line-by-line diffs │
  │ Windows-1250 text │ (invalid       │  for that file.                   │
  │                   │ UTF-8)         │                                   │
  ├───────────────────┼────────────────┼───────────────────────────────────┤
  │ Text with one     │ binary         │ Same.                             │
  │ stray bad byte    │                │                                   │
  ├───────────────────┼────────────────┼───────────────────────────────────┤
  │ Minified JSON/JS, │ text           │ Mild: lines mode works, but gives │
  │  one huge line    │                │  no diff benefit.                 │
  └───────────────────┴────────────────┴───────────────────────────────────┘

  Why a wrong guess is harmless here

  Lines mode already handles arbitrary bytes. I just checked: 200 KB of random
  data encrypted in lines mode decrypts back byte-identical. And decrypt reads
  the mode from the file's first line, so nobody ever has to know what was
  guessed. A miss only costs the secondary properties: diff-friendliness, size
  (lines mode was about 8% larger on that random file) and how much structure
  stays visible.

  The real risk: a file that flips mode between versions

  That is the case to design for, not the detection itself. If config.yml is
  detected as text today and someone pastes a bad byte into it tomorrow, auto
  would switch it to blob, and the whole encrypted file would change in git
  instead of one line. The reverse flip leaks structure that was hidden before.

  The fix is straightforward: when the output file already exists (the
  auto---previous case), keep its mode and do not detect again. Detection would
  then only happen the first time a file is encrypted.

  Decisions to make if we build it

  1. Default or opt-in. I recommend opt-in (--mode auto), keeping lines as the
     default. Changing the default would silently change what existing commands
     produce for some files.
  2. How much to inspect. The whole input, not just the first 8000 bytes: the
     tools read the entire input into memory anyway, and it removes the "binary
     data starts late" miss.
  3. Empty input. Treat as text (lines).
  4. Format. No change to ssenc1: auto is only a choice made by the encrypting
     side, and the file records lines or blob as today.
  5. Scope. It has to be added to all three implementations with identical
     rules, plus the cross tests, docs and an example. In Bash the UTF-8 check
     is the awkward part (probably iconv or a perl-free byte-pattern check), so
     that is where most of the effort would go.

  My recommendation: build it as opt-in --mode auto with the NUL + UTF-8 rule
  over the whole input, and "existing output keeps its mode".

  What --chunk 16384 does

  Blob mode does not lock the whole file as one piece. It cuts the file into
  pieces of a fixed size and locks each piece separately, each with its own
  tamper seal. --chunk 16384 sets that piece size to 16384 bytes (16 KiB)
  instead of the default 65536 (64 KiB).

  - Your 20 KB image: with the default it is one piece; with --chunk 16384 it is
    two.
  - Security: the same. Every piece is sealed, and their order and count are
    checked too.
  - Size: each piece adds 16 bytes for its seal, so smaller pieces make the file
    slightly bigger.
  - Diffs: this is the only practical reason to change it. If a few bytes of a
    binary file are overwritten in place, only the pieces containing them change
    in the encrypted text, so smaller pieces give smaller git diffs. If bytes
    are inserted or removed, everything after that point shifts and changes
    anyway.
  - Decrypting: needs no option; the piece size is written in the first line of
    the file (#ssenc1 blob chunk=16384).

  For most files the default is fine.
